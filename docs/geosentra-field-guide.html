01

GEOSENTRA in one paragraph

GEOSENTRA is a disaster-intelligence and relocation-planning application. It is built to help a disaster authority see which populated areas ("habitations") are at risk from landslide, flood, coastal erosion or cloudburst; understand who lives there and how vulnerable they are; find and evaluate safe places to move people to; plan the safest travel route for that move, tailored to who is travelling; and keep a record of every decision made along the way. Right now, everything in the application — every map, every number, every risk score — is a working frontend prototype running on realistic but invented data. There is no live backend, no live sensor feed, and no trained machine-learning model behind any of it. The value of what exists today is that the full decision-making experience is real and usable: the screens, the navigation, the role permissions, and the underlying calculation logic are all genuinely built and tested — they are simply fed by carefully constructed example data instead of a live government data feed.

02

What problem the application solves

In a disaster, the hardest questions are rarely "is there a hazard?" — they are: which specific communities are actually in danger right now, how many people, of what kind, need to move, where can they safely go, and how do they get there without walking into a second hazard? Answering these questions well requires combining several kinds of information that are normally scattered across different departments and paper records: hazard maps, population and vulnerability records, the physical capacity of relief camps and relocation sites, and road conditions.

GEOSENTRA's design goal is to bring all of that into one connected screen, so that a decision like "relocate Kovalam East to the Community Development Zone" is backed by a visible, explainable chain of reasoning — risk score, population profile, site capacity, distance and route safety — instead of being made from memory or a phone call. The prototype demonstrates how that connected decision screen would work, using realistic mock data in place of the live feeds a production deployment would eventually need.

USP

Unique Selling Proposition

Most disaster-management tools actually available to a district or state today are one of two things: a static hazard map with no connection to who lives in the affected area, or a records system with no map at all. GEOSENTRA's differentiator isn't any one feature — it's that the pages below hand off to each other, so one browsing session can go from "where is the hazard" to "who is affected" to "where can they go" to "how do they get there," without switching tools. Every point below is something the current frontend does today, not a planned feature.

A. A unified disaster-management interface

Overview, Hazard Intelligence, Habitations, Safe Sites, Route Intelligence, Institution / Evacuation, and All Relocations Across India share the same underlying habitation, safe-site and risk data — a number shown on Overview always agrees with what Habitations and Safe Sites show for the same place.

B. Hazard-to-habitation navigation is a real click path

A hazard map checkpoint, a name inside the High Risk box, and a name inside the Moderate Risk box all call the same navigation logic and land on that exact habitation's own detail page — confirmed by clicking different items and getting different, correct destinations.

C. Relocation-aware Route Intelligence

Selecting a record on All Relocations Across India — or a habitation, safe site, or evacuation group elsewhere — opens Route Intelligence pre-loaded with that specific source and destination, not a fixed example pair. The route itself is generated locally between two real coordinates, on the current frontend/mock implementation, not returned by a live routing service.

D. Visual risk prioritization

Risk is colour-coded consistently everywhere: red for the High Risk box and Critical/High-Risk badges, orange/amber for the Moderate Risk box and Watch-tier badges, green for Normal/Low tier — and safe sites render as a distinct green box marker so they can't be mistaken for any other marker type at a glance.

E. Map-based decision support

The maps let a user see hazard zones, habitations, safe sites, and — on Route Intelligence and the National Relocations map — relocation routes together, and click through to detail on any of them. This supports planning and review; it is not live emergency navigation — there is no GPS, no live traffic, and no real routing engine, and the app says so on-screen.

F. A role-oriented workflow

Exactly four login roles are implemented — Disaster Authority, Volunteers, Citizen, and Emergency Coordinator — each with a different Overview dashboard and a different, permission-checked set of pages (see Section 04), so a citizen and an authority are never shown the same screen.

G. Frontend-first and cost-conscious

The entire experience above runs on existing frontend components, mock data, and free OpenStreetMap tiles — no backend, no database, and no paid API required to build or demonstrate it. That keeps it cheap to build and easy to evaluate, while being honest that it is not yet production-ready (see Feasibility, next).

GEOSENTRA's core USP is the integration of hazard awareness, habitation-level risk detail, safe-site identification with real capacity limits, and source-to-destination route intelligence into one role-aware, click-through disaster-management frontend — demonstrated end-to-end today on mock data, and structured so a real backend and live data sources can be substituted in later without redesigning the interface.
FEAS

Feasibility

Can GEOSENTRA realistically be built, demonstrated, and grown? This section separates what's already proven by the running prototype from what production use would still require.

A. Technical feasibility

Not aspirational — every page, map, risk category and route-display flow described in this document is already running in the deployed prototype, built entirely from React 19, Vite, react-router-dom v7, Leaflet/react-leaflet on free OpenStreetMap tiles, Tailwind CSS v4, and three React Contexts for state (no external state library needed at this size). Source control is GitHub; hosting is Vercel — both already in active use for this project.

B. Operational feasibility

A user can already move through the full intended workflow: role-specific Overview → identify Low/Moderate/High/Critical habitations → open a habitation's full detail → compare safe sites against real capacity limits → review relocation records → open a source-to-destination route. Colour-coded risk, clickable markers and risk boxes, and a role-filtered menu make this usable today for review, training and demonstration. It has not been tested with real disaster-authority staff or emergency teams, and no government or emergency body is claimed to be using it.

C. Economic feasibility

Cost-conscious by construction: open-source frontend tools, free map tiles with no billing account, GitHub, and Vercel — no backend, database, or paid API needed to build or demonstrate the current prototype. A future production deployment would add real costs this document does not estimate — backend hosting, a managed database, live hazard/routing data licensing, authentication infrastructure, monitoring, and higher map-tile usage — because no such figures currently exist in this project's documentation.

D. Schedule feasibility

Built incrementally, and the repository history reflects it: (1) interface & navigation, (2) map & markers, (3) hazard & habitation interactions, (4) safe-site visualization, (5) relocation records, (6) Route Intelligence integration, (7) responsive/testing pass — all done. (8) Backend & live-data integration is a future phase, not started.

E. Scalability feasibility — future enhancements, not current features

Backend integration and a real database, live hazard data feeds, IoT/sensor integration, a trained ML risk model, dedicated authority dashboards, citizen reporting, real push/SMS/email notifications, offline support, multilingual support, more Indian regions, real-time traffic-aware routing, persistent audit logging, and finer-grained role permissions.

F. Legal, security and data feasibility

The current session is a mock, local-only login with no password and no server check — appropriate for a demo, not for production. Real deployment would need secure authentication, server-enforced role-based access control, protection of sensitive location/population data, secure API communication, input validation, documented privacy practices, verified data sources, backup/recovery, and persistent audit logging. This prototype should not be presented or deployed as an official emergency-response system until that work is done.

Overall conclusion: GEOSENTRA is technically feasible as a frontend prototype — that feasibility is demonstrated, not projected. The core workflow is built and working today on mock data, deployed via GitHub and Vercel, and structured to accept a real backend and live data later without a rewrite. Production or emergency use would additionally require the validation, data sourcing, and security work above, which has not yet been done.

03

Who uses GEOSENTRA

The application is built around four distinct logged-in perspectives, each seeing a different dashboard and a different set of pages, plus the general public who can view the marketing page before choosing a role. The four roles are described fully in the next section; in short:

  • Disaster Authority — the decision-maker: the only role that can see literally everything, including national-level monitoring and audit records.
  • Volunteers — people supporting relocation and shelter work on the ground.
  • Citizen — a resident who wants to know if they're at risk and how to reach safety.
  • Emergency Coordinator — the operational role running evacuation and movement during an active event.
04

Complete login and role explanation

The code defines exactly four roles, confirmed directly in the authentication configuration file. There is no fifth hidden role and no separate admin account. Logging in is a simulated action: choosing a role card creates a local browser session with no password and no server check — this is stated explicitly on-screen on the role-selection page itself, and is not something this review is inferring.

About the name "Institution." An earlier version of this project used "Institution" as the name of one of the four login roles. That role has since been fully renamed to Volunteers — not just the on-screen label, but the underlying role identifier the code uses internally as well. The word "Institution" still exists in the application today, but only as the name of a completely different, unrelated feature: the Institution / Evacuation page, which manages evacuation planning for schools, colleges, hospitals, care homes and community centres. That page's name has nothing to do with the login role — it was never renamed because it was never the same thing. See page 10 in Section 6 for that feature in full.

1 · Overview

Purpose. This is the home screen after logging in — a single-glance situation report. It is deliberately different for each role, because "the overview a citizen needs" and "the overview an authority needs" are genuinely different questions.

Route
/app
Access
All four roles

What the user sees

Disaster Authority & Emergency Coordinator get the full "operational view": eight statistic tiles — Low Risk Habitations, High-Risk Habitations, Critical Red Zone Habitations, People Requiring Immediate Relocation, Vulnerable Population Tracked, Available Safe-Site Capacity, Capacity Shortage, and Moderate Risk Habitations — followed by a four-tile Hazard Overview (one per hazard type), the main map, a Priority Habitations / Active Incidents list, and (for Authority only) a Recent Decisions feed pulled from the Audit Trail.

Volunteers see four tiles about the specific institution they are currently supporting, plus a card naming that institution with quick links to its evacuation plan and a safe route.

Citizens see four tiles about their own home area — its status, the nearest hazard, the nearest safe site, and a shortcut to the safest route — plus an Emergency Instructions card and a reminder that this is a demonstration.

What the user can do

  • Click any statistic tile to jump to the page it summarises (e.g. the risk tiles jump to Habitations; capacity tiles jump to Safe Sites).
  • Toggle map layers on and off: Hazard Layers, Population, Infrastructure, Safe Sites.
  • Click any marker on the map (see Section 8 for exactly what each click does).
  • Click a Priority Habitation / Active Incident row to open that habitation.

Real-world meaning

This is the equivalent of the first screen a duty officer checks at the start of a shift: how many places are safe, how many are worsening, and is there anything that needs attention right now.

Every number on this page is calculated live from the same eight mock habitations and six mock safe sites used everywhere else in the app — it is not a separately hand-typed number, so it always agrees with what the Habitations and Safe Sites pages show.

Route

Access

What the user sees

  • Four toggle chips, one per hazard type, that show or hide that hazard's shaded zones on the map.
  • A map with colour-shaded hazard zones (Safe / Moderate Risk / High Risk / Red Zone-Critical) and every habitation shown as a marker.
  • An "Active Layers" card: a qualitative HIGH/MEDIUM tag for each of the four hazards, plus one combined-risk number.

What the user can do

  • Click a shaded hazard zone on the map to open a detail panel: hazard type, affected area, hazard-specific technical fields (e.g. slope and soil stability for a landslide zone; water level and flood depth for a flood zone), a confidence bar, and a "last updated" note.
  • Click any habitation marker on the map to open that habitation's own detail page.
  • Click any habitation name inside the High Risk or Moderate Risk box to open that exact habitation's detail page — the same destination as clicking its map marker.
Verified directly: clicking "Perungalathur" inside the High Risk box opens /app/habitations/perungalathur; clicking "North Ridge Basti" inside the Moderate Risk box opens /app/habitations/north-ridge-basti. Two different items, two different destinations — not one shared page.
What used to be here and no longer is: this page previously showed a page-level "Risk Score / Confidence / Today HH:MM / data quality / missing healthcare data" summary block, plus a standing "Frontend data status: mock data..." disclaimer, plus a plain ranked list called "Most Exposed Habitations." All three have been removed. Risk Score is now configured in Settings and shown per-habitation on the Habitation Detail page; the ranked list has been replaced by the two clickable risk boxes above; the disclaimer panel has been intentionally left off this specific page (it still appears on most other pages).

Are the risk values real? No. Every hazard zone's numbers are hand-authored mock figures, and every habitation's risk score is calculated by a documented formula from mock inputs (see Section 9). The zone detail panel itself states "Mock prediction — backend not connected."

Simulated routingFully working prototype

Purpose. Answers "how does this specific group of people get from here to safety, and what should they watch out for on the way" — tailored to who is travelling, not a one-size-fits-all direction.

Route

What the user sees

This should not be described as a full volunteer coordination feature; it is the visible groundwork for one.

8 · What-If Simulator

Frontend calculationFully working prototype
▶

Purpose. Lets a planner ask "what happens to every one of our numbers if conditions get worse (or better)?" before it actually happens — a rehearsal, not a forecast.

Route
/app/what-if
Access
Disaster Authority, Emergency Coordinator only

What the user can change

Eight sliders: Rainfall Intensity, Flood Depth, Landslide Susceptibility, Coastal Erosion Rate, Cloudburst Intensity, Drainage Capacity, Road Accessibility, and Population Vulnerability — each labelled with exactly which hazard(s) it affects.

What happens when values change

Every habitation's risk score is recalculated live, using the exact same formula the rest of the app uses (see Section 9) — this scenario is shared app-wide the moment it changes, so Overview, Hazard Intelligence, Habitations and Route Intelligence all reflect it immediately, not just this page.

What results are shown here

  • A before/after table of the same eight dashboard metrics used on Overview, with the exact change for each.
  • A list of exactly which habitations crossed a Red Zone tier boundary under this scenario, and their new relocation timeframe.
  • A before/after comparison of how the three illustrative routes would be ranked for the currently-selected traveller profile.

A scenario can be saved to one temporary slot and reloaded, or reset back to baseline.

The complete application working flow

From opening the browser to a decision being logged. Every step below is something the current code actually does — none are hypothetical.

Step 1 — Opening the application

The first screen anyone sees, logged in or not, is the public Landing page — a pitch explaining what GEOSENTRA does, ending in an "Explore Platform" button. There is no username/password form anywhere; "logging in" means picking a role card on the next screen. Step 2 — Role selection and login

Clicking through leads to /role-select, showing four role cards (Disaster Authority, Volunteers, Citizen, Emergency Coordinator). Picking one instantly creates a browser-only session and opens that role's Overview dashboard — no server round-trip, no password. Logs in → reviews the Command Center Overview → opens Hazard Intelligence or a specific Habitation → checks relocation destinations and their capacity limits → allocates people to a site in Relocation → checks the route → configures Risk Score thresholds or reviews the audit log as needed → monitors nationwide progress in All Relocations Across India.

Emergency Coordinator

Logs in → reviews Active Incidents → opens Hazard Intelligence and Habitations to see who's affected → coordinates a route and, if needed, an evacuation plan through Institution / Evacuation → tracks progress alongside Disaster Authority (without the audit and national views).

Risk, safety, capacity, and relocation terminology

These terms sound similar but mean genuinely different things in the code. Confusing them is the single easiest way to misrepresent what the application does.

Risk tiers (a habitation's status)

LabelColourScore range (default)What it meansResulting timeframe
Normal LowGreen0–39No urgent concern under current conditionsMonitor Only
Watch ModerateAmber40–64Worth watching closely; conditions could worsenMedium-Term
High RiskOrange/Red65–84Should begin preparing to relocateShort-Term
Critical Red ZoneDark Red85–100Unsuitable for continued habitation right nowImmediate

The numeric Risk Score that decides which tier a habitation falls into is calculated, not looked up: Hazard Intensity × 0.40 + Population Vulnerability × 0.25 + Disaster History × 0.20 + Infrastructure Constraint × 0.15, then nudged slightly toward the middle when data confidence is low. Confidence is a separate number describing how reliable the underlying data is — a habitation can have a high risk score and low confidence at the same time, which the app flags separately rather than blending the two together.

Safe-site terms

Safety Score
How structurally/geographically safe the site itself is — a property of the site alone, independent of who might move there.
Effective Capacity
The smallest of the site's six resource capacities (physical space, water, medical support, sanitation, food, accessibility) — the real ceiling, because a site with huge open land but tiny water supply can still only support as many people as its water can serve.
Bottleneck limitations
In plain terms: whichever one of those six resources is the weakest — the specific thing actually limiting how many people this site can safely take in. It is not a general summary of the site; it names one specific constraint.
Current Load
What percentage of effective capacity is already occupied or reserved.
Available Capacity
Effective Capacity minus what's already occupied or reserved — the actual remaining room.
Suitability
A different number from Safety Score: it blends the site's safety with how well it fits this specific habitation right now — available room relative to that habitation's population, road access, and livelihood continuity. A safer site can score lower here than a slightly-less-safe one if it can't hold everyone.

What is required next to make this a real working system

  1. A real hazard data feed — from meteorological, geological or satellite sources — to replace the hand-authored hazard zones.
  2. A trained risk model per hazard type, replacing the current fixed formula, with the model's own confidence output feeding the existing confidence display.
  3. A backend and database to store habitations, safe sites, institutions, allocations, and the audit trail permanently — the frontend's calculation logic (risk, capacity, suitability, routing) is already shaped to be handed real numbers instead of mock ones, since it was deliberately built to be swapped out one function at a time.
  4. Real authentication and accounts, replacing the mock role-selection login, with real permission enforcement on a server rather than only in the browser.
  5. A real routing engine (road-network aware, ideally with live traffic/road-closure data) to replace the illustrative straight-line-with-bend routes.
  6. Real notification delivery (SMS, push, email) for the Alerts feature, instead of only appearing while the app is open.
  7. Connecting the Risk Score settings in Settings to the actual scoring engine, so changing a threshold there changes what the rest of the app classifies as Low/Moderate/High/Critical.
  8. A volunteer task/assignment system — sign-up, task claiming, hours or contribution logging — to make the Volunteers role a complete workflow rather than a viewing role.
  9. Persistent audit logging, so decisions survive a page refresh and a server restart, not just the current browser tab.
17

Final conclusion

GEOSENTRA today is a complete, working demonstration of how a disaster-relocation decision-support system should feel to use: four clearly separated roles, a full chain from hazard to habitation to relocation destination to safe route, transparent reasoning behind every number, and a national-level view for oversight. Every screen described in this document was opened and exercised directly to confirm it — the risk-box clicks, the four different national-relocation routes, the role-restricted pages, the search filters — none of it is assumed from reading code alone.

What it is not, and does not claim to be, is a live disaster-monitoring system. There is no government data feed, no trained model, no real accounts, and no persistent storage behind any of it. That distinction is not a weakness to hide — the project's own interface says so, page after page, in plain language. The honest way to present GEOSENTRA to a judge, an official, or a partner is exactly that: a fully-realised user experience and decision logic, built and ready to be connected to the real data sources listed in Section 16, rather than a finished production system.

Prepared by inspecting the GEOSENTRA frontend codebase directly — routing files, role configuration, page components, and mock data files — and by exercising the running application across all four roles. Where a claim could not be confirmed from the code or by direct testing, it has been stated as such rather than assumed.
